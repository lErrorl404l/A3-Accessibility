# Arma 3 colour surface and moddability

Source of record for which config classes this addon overrides. **Confidence caveat:** the
Bohemia Interactive Community Wiki (BIKI) returned HTTP 403 to the research fetcher, so items
whose only authority is the BIKI are marked UNVERIFIED. Class names given as VERIFIED are
confirmed against reachable engine/tool source. Where the AEE prior art
(`docs/research/05-aee-prior-art.md`) provides a verified in-workspace example, that is the
authority and is preferred over inference.

## 1. Where colours live

| Class | Status | Notes |
|---|---|---|
| `CfgMarkerColors` | VERIFIED | Named palette. `setMarkerColor "ColorBLUFOR"` resolves the name here at runtime |
| `CfgMarkerClasses` | VERIFIED | Groups marker icons; grouping only |
| `RscStructuredText` (+ `RscText`, UI controls) | VERIFIED | `colorText[]`, `colorBackground[]` are 4-element RGBA |
| `CfgInGameUI` | Class exists (CBA forward-declares it) | Specific colour keys UNVERIFIED |
| `CfgHud` | NOT FOUND | No Arma usage found; likely a misnomer. Do not plan around it |
| `CfgVehicles` marker colour | NOT CONFIRMED | Probably a false lead. A unit's map colour comes from side/marker colour, not a vehicle colour field |

Sources: SQFvm `ops_markers.cpp` (name resolution), BohemiaInteractive/CWR map dialogs,
zen-mod/ZEN `markers_tree` (CfgMarkerClasses), CBA `script_classes.hpp` (CfgInGameUI exists),
CBA `diagnostic/gui.hpp` (RscStructuredText), KP-Liberation (`colorText[]`/`colorBackground[]`).

### The stable hook

Marker **names** are the stable interface. A mission script calling `setMarkerColor "ColorBLUFOR"`
resolves through `CfgMarkerColors` at runtime, so redefining `ColorBLUFOR` in an addon changes
that marker's colour **without touching the mission**, provided the mission uses the name and not
a raw RGBA array. This is the core mechanism for a colour-blind remap.

Confirmed colour names in shipped content: `ColorBLUFOR`, `ColorOPFOR`, `ColorCIV`, `ColorGrey`,
`ColorRed`, `ColorBlue`; plus side-mapped `ColorBLUFOR`/`ColorOPFOR`/`ColorIndependent`/`ColorCivilian`
(names UNVERIFIED except those seen in sources).

## 2. What an addon can and cannot change

| Element | Addon-overridable | Confidence |
|---|---|---|
| Named marker colours (`CfgMarkerColors`) | Yes, redefine entries | Class VERIFIED; override syntax UNVERIFIED by this source, but VERIFIED by AEE prior art |
| Marker icon categories (`CfgMarkerClasses`) | Yes | VERIFIED |
| Map friend/foe colour | via the palette name | UNVERIFIED |
| Mission/editor marker colours | only the names the mission references; cannot rewrite a mission's raw RGBA | UNVERIFIED |
| HUD colours (`CfgInGameUI`) | Likely yes; keys UNVERIFIED | UNVERIFIED |
| UI control colours (`RscStructuredText` etc.) | Yes, for UI the addon defines | VERIFIED |

Cannot do for free: rewrite another mission's scripts or a raw RGBA array baked into a mission;
change colours generated by the engine outside config (set UNVERIFIED without the BIKI).

## 3. Colour value format

- RGBA array, components 0..1, four numbers: red, green, blue, alpha. VERIFIED.
- Alpha is the **fourth** element and is opacity: `1` opaque, `0` invisible. VERIFIED.
- `colorText[]` / `colorBackground[]` take the same four-element form. VERIFIED.
- Hex (`#RRGGBB`, `#RRGGBBAA`) is used inside structured-text strings, not in config colour
  arrays; accepted contexts and alpha position UNVERIFIED.

## 4. The native colour-blindness setting is unconfirmed

The full Arma 3 Steam news archive (1000 items, 2015-03-10 to 2026-10-01) contains **no mention**
of colour blindness, protanopia, deuteranopia or tritanopia. Arma Reforger's archive likewise
contains none. The named "protanopia/deuteranopia/tritanopia" filters in the original brief look
like options from another product or a community mod.

Finding: treat "Arma 3 has a native colour-blind setting" as **UNCONFIRMED**. If it exists, its
mechanism (post-process vs palette) is UNKNOWN. This does not block the mod; if anything it
strengthens the case that the feature is missing.

## 5. Is CBA needed?

Yes, for this design. A pure palette override needs no framework, but a **user-selectable, persisted
mode** is exactly what CBA's settings framework exists for. CBA is justified by the selectable mode,
not by the colour override.

## 6. Verification backlog (do before finalising the config)

1. Read the BIKI in a normal browser: `CfgMarkerColors`, `CfgMarkerClasses`, `CfgInGameUI`,
   `RscStructuredText`, `mod.cpp`, `PBO`, `__has_include`. This closes most UNVERIFIED items.
2. Confirm in-game whether any native colour-blindness option exists (Options > Video/Game). If
   not, state the mod as "building the missing feature".
3. Discard `CfgHud` unless the BIKI says otherwise.
4. Dump the vanilla `CfgMarkerColors` and `CfgInGameUI` config from a game install to get exact
   keys and the current palette, rather than inferring them.

Items 1 and 4 are the highest value and are deferred, not blocked: the AEE prior art already gives
a verified working `CfgMarkerColors` shape to build against now.

## 7. BIKI retrieval (Wayback Machine, 2026-10-12)

The live BIKI returns 403 to automated fetches. Snapshots were read through the Wayback CDX API
and a retrieval proxy.

### `Arma_3:_CfgMarkerColors` - RETRIEVED (snapshot 2025-04-18)

Field semantics confirmed: `color[] = {r, g, b, a}` (RGBA), `name` (display name in UIs),
`scope = 1` means public and `scope = 0` means private.

The full vanilla palette is now known (RGBA, alpha 1):

- `Default` {0,0,0,1}, `ColorBlack` {0,0,0,1}, `ColorGrey` {0.5,0.5,0.5,1}, `ColorRed` {0.9,0,0,1},
  `ColorBrown` {0.5,0.25,0,1}, `ColorOrange` {0.85,0.4,0,1}, `ColorYellow` {0.85,0.85,0,1},
  `ColorKhaki` {0.5,0.6,0.4,1}, `ColorGreen` {0,0.8,0,1}, `ColorBlue` {0,0,1,1},
  `ColorPink` {1,0.3,0.4,1}, `ColorWhite` {1,1,1,1}.
- Side classes: `ColorWEST` {0,0.3,0.6,1}, `ColorEAST` {0.5,0,0,1}, `ColorGUER` {0,0.5,0,1},
  `ColorCIV` {0.4,0,0.5,1}, `ColorUNKNOWN` {0.7,0.6,0,1}. Lower-case aliases `colorBLUFOR`,
  `colorOPFOR`, `colorIndependent`, `colorCivilian` carry the same values.

This confirms the five engine class names used by the plan (`ColorWEST`, `ColorEAST`, `ColorGUER`,
`ColorCIV`, `ColorUNKNOWN`) and their current values.

### `Class_Inheritance` - RETRIEVED (snapshot 2025-03-24)

- An external base class needs a skeleton declaration first: `class externalBaseClass;`.
- `delete ClassName;` removes an existing class. A parent cannot be deleted before its children.
- `requiredAddons[]` sets load order. `A3_Data_F_Decade_Loadorder` is the last vanilla `CfgPatches`
  entry as of Arma 3 2.14, so it can be used to overwrite some vanilla configs.

### `PreProcessor_Commands` (`__has_include`) - RETRIEVED (snapshot 2025-05-05)

- `__has_include` returns 1 if a file exists, else 0, and was introduced in Arma 3 2.02.
- The path must start with a backslash, or it fails silently and returns 0.
- A config that changes with loaded mods must not be binarized.

### Still UNVERIFIED from BIKI (no capture exists)

`CfgMarkerClasses` fields, every `CfgInGameUI` colour key, `RscStructuredText` colour keys and the
inline text colour tag, and the `Mod.cpp` fields. For these, the AEE prior art and the engine-config
surface docs remain the authority.

Net effect on the plan: the five engine class names and their current values are now confirmed, so
